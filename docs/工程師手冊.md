## 1. 第一天要做的事

1. 取得：GitHub repo 權限、Netlify 站台權限、Supabase 專案權限、一個測試用 LINE 官方帳號（不要用正式的）
2. 讀 `系統規格書.md` 第 1、3、4、6.1、6.2、6.3 章——這五節是理解一切的基礎
3. 本機跑起來（第 4 節），`npm run test:flow` 全過
4. 用測試帳號跑一次規格書 6.2.6 的典型對話，同時在後台「AI 客服中心 → 對話紀錄」看每句話的「處理過程」——這是理解對話流程最快的方式
5. 讀 `netlify/functions/line-webhook.ts` 的 `processLineEvent()` 和 `handleQuoteConversation()` 兩個函式，其他先不用

### 2.1 `line-webhook.ts` 的結構

檔案很大，但分區清楚。由上而下：

| 區 | 內容 |
|---|---|
| 基礎設施 | `deferWrite` 延後寫入佇列、`runTurn`／trace（處理過程診斷）、`logConversation`、快取（settings、channels、flows、message variables，各 30 秒～5 分鐘） |
| `handler` | 驗簽章、辨識官方帳號、把事件依客人分組平行處理（同一客人序列） |
| `processLineEvent` | 規格書 6.1 的流程圖，逐關卡判斷 |
| session 與鎖 | `loadBookingSession`／`saveBookingSession`、`acquireFlowLock` |
| 欄位擷取 | `extractStepFields`（AI）、`extractStepFieldsWithoutAi`（規則：日期／人數／房數／標籤） |
| 流程進入點 | `startBookingFlow`、`tryStartQuoteFromCompleteInfo`（冷啟動）、`continueBookingFlow` |
| **報價流程分派** | `handleQuoteConversation` → `classifyBookingIntent` → 依意圖呼叫 `advanceCollecting`／`confirmQuote`／`declineQuote`／`requoteWithCollected`／`restartQuote`／`handleRemittanceReport`／`handleUnclear` |
| 報價 | `finishBookingFlow`（衝突檢查、引擎、寫訂單、候補）、`checkBookingConflict`、`findOverlappingLiveBooking` |
| 候補 | `findWaitlistWatchTarget`、`attemptWaitlistRetry`、`processWaitlist` |
| AI 呼叫 | `callGPT`（含 Responses API 分支）、`callGemini`、`extractResponsesApiText`、知識庫檔案快取 |
| 測試出口 | `quoteFlowDeps`（可覆寫的重機械）、`__quoteFlowTesting` |

### 2.2 資料怎麼流

```
LINE ──POST──▶ line-webhook ──▶ Supabase (service role)
                    │
                    ├─▶ OpenAI / Gemini（意圖分類、欄位擷取、問答）
                    └─▶ LINE reply/push（回客人、通知客服）

後台（瀏覽器）──anon key + JWT──▶ Supabase（受 RLS）
        └──Bearer JWT──▶ 各 Function（requireRole 檢查）──service role──▶ Supabase

Netlify cron ──▶ scheduled-tasks-run ──▶ Supabase / LINE push / Google Calendar / OTA iCal
```

## 3. 這個專案的慣例

### 3.1 註解寫「為什麼」，用中文

每個非顯然的決定都有一段註解解釋**為什麼這樣做、不這樣做會發生什麼**，常帶當初踩到的實際案例。這是刻意的：接手的人要能從註解知道哪些「奇怪的寫法」是刻意的、動了會出事。改程式時請維持這個習慣——刪掉一段防護前先讀它上面的註解。

### 3.2 schema 可重複執行

`supabase_schema.sql` 從頭到尾可以整份重跑：`CREATE TABLE IF NOT EXISTS`、`ADD COLUMN IF NOT EXISTS`、`DO $$ ... $$` 動態檢查後才建 policy。**新專案和既有專案升級用同一份檔案**，所以：

- 新增欄位一律 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，不要改 `CREATE TABLE` 裡的定義（既有資料庫不會重跑 CREATE）
- 改 CHECK 約束的順序是：**先 DROP 舊約束 → UPDATE 搬遷既有資料 → 再 ADD 新約束**。順序錯了 UPDATE 會被舊約束擋下（這個坑踩過兩次）
- 舊欄位不刪，加註【已停用】（見第 10 節）

### 3.3 金額與房間絕不交給 AI

`bookingEngine.ts` 是純函式、無副作用，所有價格由它算。AI 的角色只有三個：分類意圖、抽欄位、回答知識庫問題。如果你想「讓 AI 幫忙算個價」——不要。

### 3.4 狀態只定義一次

訂單狀態在 `bookingStatus.ts`，帳號狀態與角色在 `permissions.ts`，官方帳號角色在 `lineChannels.ts`。前端顯示、後端判斷、排程都 import 這些。加狀態改一個地方。

### 3.5 回覆先送，紀錄後寫

`deferWrite()` 把「沒人在等結果」的寫入（對話紀錄、聯絡人時間）排進佇列，回覆送出後、`handler` return 前一次 `flushPendingWrites()`。**Serverless 容器 return 之後就凍結**，所以不能真的 fire-and-forget，一定要在 return 前 await 完。

### 3.6 每支 Function 的固定樣板

```ts
const rawHandler: Handler = async (event) => {
  if (event.httpMethod !== 'POST') return { statusCode: 405, body: 'Method Not Allowed' };
  const guard = await requireRole(supabaseAdmin, event as any, ['admin']);   // 需授權時
  if ('error' in guard) return guard.error;
  // ...
};
export const handler: Handler = withErrorLogging(supabaseAdmin, 'function-name', rawHandler);
```

`requireRole` 檢查 JWT、帳號狀態 `active`、2FA 等級 `aal2`、角色；`withErrorLogging` 把 4XX／5XX 與例外寫進 `operation_logs`。Functions 用 service role **繞過 RLS**，授權全靠這一行，漏了就是任何登入者都能呼叫。

### 3.7 兩套 UI 元件並存

`src/components/ui/`（Tailwind）是舊的，`ui-mui/`（MUI）是新的。新頁面用 MUI 版；改舊頁面時不用順手搬，除非整頁重寫。`Login.tsx`、`AiServiceCenter.tsx`、`KnowledgeBase.tsx`、`SystemSettings.tsx` 等仍是 Tailwind。

### 3.8 快取有 TTL

settings 30 秒、line_channels 30 秒、booking_flows 30 秒、message_variables 5 分鐘、知識庫檔案內容 5 分鐘。後台改完不是立刻生效；測試時等一下再試，不是壞掉。

### 3.9 處理過程要留痕

在 `line-webhook.ts` 的對話路徑上做判斷時，用 `traceStep('人看得懂的一句話')` 記下走到哪、為什麼；重要資料用 `traceData(key, value)`；錯誤用 `traceError()`。這些會出現在後台的「處理過程」，是客服和你排查問題的主要工具。沒留痕的新分支等於黑箱。

### 3.10 Commit message 寫問題與原因

看 `git log`：每則 commit 的第一段講「客人／使用者遇到什麼」，接著講「程式為什麼會這樣」，最後才是「改了什麼」。維持這個寫法，半年後查 `git blame` 才看得懂。

## 4. 本機開發

### 4.1 需要的東西

- Node.js 18+（Functions 目標是 node18）
- 一個 Supabase 專案（可以是自己的測試專案，跑一次 `supabase_schema.sql`）
- `.env`（不進版控）：
  ```
  VITE_SUPABASE_URL=https://xxx.supabase.co
  VITE_SUPABASE_ANON_KEY=...
  ```

### 4.2 指令

| 指令 | 做什麼 |
|---|---|
| `npm run dev` | Vite 前端（localhost:5173）。**Functions 不會跑**，需要 Functions 時用 `netlify dev` |
| `netlify dev` | 前端 + Functions 一起（需 `netlify login` 並 `netlify link`），Functions 的環境變數從 Netlify 拉 |
| `npm run typecheck` | 前端 + Functions 兩份 tsconfig 都跑 |
| `npm run lint` | ESLint，零警告才過 |
| `npm run build` | 型別檢查 + Vite build |
| `npm run test:flow` | 對話流程測試（見 7.4） |

改動送出前四個都要過：`typecheck`、`lint`、`build`、`test:flow`。

### 4.3 只看前端頁面的話

`.env` 填假值也能跑起前端（會顯示「設定未完成」以外的頁面骨架），但登入會失敗。要看需要登入的頁面，在 `App.tsx` 臨時加一個公開路由掛你要看的元件，看完**一定要拿掉**（`grep -rn "__" src/App.tsx` 確認）。

### 4.4 測 LINE 對話

本機收不到 LINE webhook（LINE 要打公開網址）。做法：推到 `dev-online` 讓 Netlify 部署，用測試官方帳號打。改對話邏輯時先靠 `test:flow` 把情境測過，再上去實測。

## 5. 部署與資料庫升級

### 5.1 部署

`git push origin dev-online` → Netlify 自動 build 並部署。Netlify 的 build 是 `npm run build`（含型別檢查），型別錯會讓部署失敗——這是保護，不要繞。

### 5.2 資料庫升級

1. 改 `supabase_schema.sql`（照 3.2 的規則）
2. 到 Supabase SQL Editor 貼**整份**執行（不要只貼你改的那段——前面的 `DO` 區塊會處理 policy 的重建）
3. 再部署程式

**順序很重要**：先 schema 後程式。新程式讀新欄位，欄位還不存在會失敗；舊程式讀新 schema 通常沒事。反過來（先程式後 schema）出過問題：對話紀錄的 `meta` 欄位還沒建時，新版 webhook 寫入失敗，整則對話消失。

### 5.3 Supabase 端的一次性設定

見 `SUPABASE_AUTH_SETUP.md`：Google OAuth、URL Configuration、邀請信樣板。新環境沒做這些**沒人能登入**。

### 5.4 環境變數

Netlify → Site settings → Environment variables：`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`VITE_SUPABASE_URL`、`VITE_SUPABASE_ANON_KEY`、`PUBLIC_SITE_URL`。LINE 與 AI 金鑰不在這裡，在後台設定。

## 6. 常見改動怎麼做

### 6.1 加一個後台頁面

1. `src/pages/Xxx.tsx`，用 `ui-mui` 的 `PageHeaderMui`／`DataTableMui`／`FilterPanel`
2. `src/App.tsx` 加 `<Route>`（包在 `<RequireAccess>` 裡）
3. `src/components/Layout.tsx` 的 `navEntries` 加選單項
4. `src/lib/permissions.ts` 的 `ROUTE_ACCESS` 加路徑與允許的角色（不加＝只有 admin）
5. 頁面寫入資料時呼叫 `logOperation()`（`src/lib/logOperation.ts`）留操作紀錄
6. 若頁面用到新表，`supabase_schema.sql` 第 9.7 節的 RLS `DO` 區塊，把表加進 `admin_only`、`config_tables` 或 `operational_tables` 陣列

### 6.2 加一個排程類型

1. `netlify/functions/scheduled-tasks-run.ts`：寫一個 `async function xxx(task, settings): Promise<{ ok, summary }>`，加進 `TASK_EXECUTORS`
2. `src/pages/ScheduledTasks.tsx` 的 `TASK_TYPE_OPTIONS` 加一筆（`value` 要跟 executor 的 key 一樣；需要範本或通知名單就設 `needsTemplate`／`needsGroup`）
3. 不要改既有的 `task_type` 值——已設定的排程會失效

### 6.3 加一個訊息變數

1. `supabase_schema.sql` 的 `message_variables` INSERT 加一筆（`variable_name`、`source`、`field_key`、`display_order`）
2. `src/lib/messageVariables.ts` 的 `buildMergeFields()`：若 `field_key` 不是資料表現成欄位，在這裡算出值
3. 排程通知用到的話，`scheduled-tasks-run.ts` 裡 select 訂單時要把欄位帶上

### 6.4 加一個系統設定

1. `supabase_schema.sql`：`ALTER TABLE public.settings ADD COLUMN IF NOT EXISTS xxx ...`
2. `src/pages/SystemSettings.tsx` 加輸入欄位（`name` 對應欄位名，`useSettings` 會自動存）
3. 讀取端用 `settings.xxx`，記得 30 秒快取
4. `docs/資料字典.md` 補說明

### 6.5 改意圖分類的行為

- **提示詞**：`src/lib/bookingIntent.ts` 的 `buildIntentPrompt()`。改完先用「處理過程」看幾個真實案例的 `intent_ai.raw` 確認模型照做
- **規則版**：同檔 `classifyByRules()`，順序就是優先權
- **分派**：`line-webhook.ts` 的 `handleQuoteConversation()` 的 `switch`
- **每次都要加測試**：`tests/booking-flow/intent.test.ts`（分類器）、`scenarios.test.ts`（整段對話）。改對話邏輯不加測試 = 下一個人會把你的修正弄壞

### 6.6 加一個 Function

1. `netlify/functions/xxx.ts`，照 3.6 的樣板
2. 前端用 `fetch('/.netlify/functions/xxx', { headers: { Authorization: \`Bearer ${session.access_token}\` } })`
3. `src/lib/operationLog.ts` 的 `LOG_FUNCTION_NAMES` 加名稱（操作紀錄頁的篩選用）
4. `npm run typecheck` 會檢查它（`tsconfig.netlify.json`）

### 6.7 改訂單狀態

1. `src/lib/bookingStatus.ts`：`BOOKING_STATUS_OPTIONS` 加狀態、決定它屬不屬於 `OCCUPYING_STATUSES`、`FLOW_STEP_STATUSES` 等集合
2. `supabase_schema.sql`：`bookings_status_check` 約束照 3.2 的順序改，`idx_bookings_occupying_dates` 索引的 WHERE 條件也要（`CREATE INDEX IF NOT EXISTS` 不會更新既有索引，要 DROP 再建）
3. 行事曆顏色、排程推進邏輯視需要調整

### 6.8 改 AI 呼叫方式

`line-webhook.ts` 的 `callGPT`／`callGemini`。GPT-5 走 Responses API，回應格式與 Chat Completions 不同——文字在 `output[].content[].text`，用 `extractResponsesApiText()` 抽，**不要直接讀 `result.output.text`**（這個 bug 讓所有 GPT-5 回覆變空字串，整個系統靜音了一陣子）。改完用設定頁「測試連線」實測。

## 7. 除錯

### 7.1 客人說 bot 回錯了

1. 後台「AI 客服中心 → 對話紀錄」找到那位客人
2. 那則訊息底下「▸ 處理過程」展開：
   - **決策過程**：走了哪條路、意圖判成什麼、理由
   - **intent_ai**：AI 分類的原文回覆——判錯是提示詞問題還是模型問題看這裡
   - **slots_applied**：抽到什麼欄位
   - **錯誤**：紅色，通常是 AI 呼叫失敗
3. 九成的問題在這裡就能定位。剩下的看 7.3

### 7.2 後台操作出錯

「系統設定 → 操作紀錄」，篩 `level = error`，有狀態碼與錯誤訊息。前端 UI 的錯誤透過 `logUiError()` 也會進來。

### 7.3 Netlify function log

Netlify → Functions → 選 function → Logs。`console.error` 都在這。webhook 簽章驗不過（401）、環境變數沒設，只有這裡看得到。

### 7.4 對話流程測試

```
npm run test:flow
```

`tests/booking-flow/run.mjs` 用 esbuild 把**真實的** `line-webhook.ts` 打包，把 `@supabase/supabase-js`、`@line/bot-sdk`、`openai`、`node-fetch` 換成 `stubs/` 底下的記憶體假件，所以測到的是真實的編排程式碼。

- `scenarios.test.ts`：完整對話情境。每個情境呼叫 `turn({ phase, collected, msg, ai })`——`ai` 是假的 AI 回覆，可以測「AI 判成 X 時系統怎麼做」而不用真的打 API
- `intent.test.ts`：分類器的規則版與解析
- 重機械（試算、成立訂單、匯款通知）透過 `quoteFlowDeps` 換成只記錄呼叫的假函式，測試斷言「有沒有被呼叫、帶什麼參數」

加情境：複製一個現有的 `t(...)` 改內容。命名格式「階段｜輸入 → 預期」。

### 7.5 AI 相關

- 設定頁「測試連線」：模型名稱對不對、金鑰有沒有效、模型會不會照指令輸出 JSON
- AI 失敗時客服 LINE 會收到 `⚠️ AI 呼叫失敗` 推播，內含原始錯誤

## 8. 常見故障與處理

| 症狀 | 原因 | 處理 |
|---|---|---|

## 9. 安全注意事項

- **service role key 只在 Functions 用**，永遠不進前端、不進 git。`.env` 在 `.gitignore`
- **每支需授權的 Function 都要 `requireRole`**。Functions 繞過 RLS，漏一支就是任何登入者都能呼叫（`accept-invite`、`invite-verify` 是刻意不用的，因為呼叫者還沒有權限）
- **RLS 是真正的防線**，前端的權限只是引導。新表一定要加進 schema 第 9.7 節 RLS 區塊的分層陣列
- **AI 金鑰、LINE 憑證存資料庫**，只有 admin 能讀（RLS）；設定頁的「測試連線」會把畫面上的金鑰送回自己的 Function，這是同一個信任邊界內
- **邀請 token 只存雜湊**；token 本身不是存取憑證，接受邀請還要 Google email 比對
- **客人個資**：對話紀錄依保留天數自動清除；主帳號可執行 `delete-customer-data` 一次清掉某客人的全部資料
- **入住密碼（`check_in_password`）是明碼**：客人到現場要能報，不能加密。只有待入住狀態才開放編輯
